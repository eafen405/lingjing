## Problem Statement

灵境竞赛组 AI+前端方向第一阶段，考核产物是 Unity 入门课程的复刻成果：把《Create With Code》录播合辑里的四个挑战各做一个并打包，再把另一门 2D 课程的完整项目做完并打包，交给群里的评审老师。

我接手时的处境：

- 仓库是空的，只有一份 agent 配置文档，交付物要从零建起
- 本机没有 Unity 环境，编辑器、IDE、许可全都要从零装
- 考核 PDF 只给了两段 B 站教程链接和"制作并打包"六个字，**没有验收清单、没有交付物命名规范、没有素材**
- 要复刻的起始文件是官方**故意写坏**的，缺陷散落在三个地方：脚本逻辑、场景里的预制体引用、预制体本身的碰撞体尺寸
- 两门课的素材分别在网盘和私信里，版本代次还与脚本实现耦合
- 评分要求"保留真实开发历史，避免完成后一次性上传"，所以 Git 提交历史本身就是交付物的一部分

结果是：没有一份可以照着做的清单，而"做完"没有客观标准，也没法证明每个交付物真的满足官方要求。

## Solution

把仓库建成包含**五个独立 Unity 挑战项目/完整游戏工程**的集合，每个都是可独立构建、可独立打包的交付物：

- 四个挑战各一个工程，完整游戏一个工程，在仓库里平行编号
- 每个交付物配一份验收清单，逐条列出官方**达成条件**、起始文件里的**缺陷**、以及**加分项**
- 缺陷按官方提示逐条修复：脚本逻辑、场景引用、预制体参数三处分开处理
- 起始文件一律采用课程的 2021.3 版，使输入方式、项目设置、素材三者同代
- 用三层缝验证：静态接线检查、Play 模式行为探针、构建产物冒烟
- 工程配置在**不开编辑器**的前提下先备好（标签、构建场景、输入设置、产品名），使编辑器只在验证和构建时才需要

## User Stories

### 作为评审老师

1. 作为评审老师，我打开仓库就能看到每个交付物对应哪份官方题目，以便核对范围是否完整。
2. 作为评审老师，我能在每个交付物目录里找到一份中文验收清单，以便逐条对照官方要求。
3. 作为评审老师，我能在清单里看到每一条达成条件和加分项都标注了完成状态，以便判断完成度。
4. 作为评审老师，我能看到每个交付物的独立 Git 提交历史，以便确认开发过程真实且渐进。
5. 作为评审老师，我能在清单里读到"官方缺陷"与"我改了什么"的对应关系，以便判断是理解后修复而非碰运气。
6. 作为评审老师，我能在验收清单里找到 Quiz 3 的十道答案，以便抽查对课程概念的理解。
7. 作为评审老师，我能在交付包里看到可双击运行的 Windows 程序，以便不装 Unity 也能验收。
8. 作为评审老师，我能在说明文档里看到项目介绍、个人感悟与技术选择理由，以便评估理解深度。
9. 作为评审老师，我能看到一段运行演示视频，以便快速核对每个交付物的实际表现。

### 作为交付物的玩家

10. 作为玩家，我按下空格能放出一只狗，它向左跑去接球，以便体验挑战二的玩法。
11. 作为玩家，我能看到天上随机落下三种颜色不同的球，以便理解"随机生成"被正确实现。
12. 作为玩家，我能接住球、看到球在接触狗的瞬间消失，而不是在远处就凭空消失。
13. 作为玩家，我看到球掉出画面下方时游戏结束并给出提示，以便理解失败反馈。
14. 作为玩家，我连续快速按空格不会刷出一长串狗，以便操作手感正常。
15. 作为玩家，我能按住空格让气球持续上升、背景无缝滚动，以便体验挑战三。
16. 作为玩家，我吃到金币看到烟花与音效、撞到炸弹看到爆炸且背景停下，以便体验挑战三的反馈闭环。
17. 作为玩家，我能用摄像机绕圈操控足球，把敌方球撞进对方球门、并防住它们撞进我的球门，以便体验挑战四。
18. 作为玩家，我每清空一波敌人，下一波敌人会多一个，以便感受到难度递增。
19. 作为玩家，我吃到力量道具后能把球撞得更远，约五秒后效果消失，以便体验增益机制。
20. 作为玩家，我点中冒出来的食物会加分并爆炸、点不中则游戏结束，以便体验挑战五。
21. 作为玩家，我能在标题界面选择难度，难度越高食物冒得越快，以便挑战自己。
22. 作为玩家，我能看到分数显示为"Score: 数字"、倒计时从 60 秒递减到 0 并结束游戏，以便有明确的胜负反馈。
23. 作为玩家，我在主菜单点 Play 进入游戏、失败后点 Restart 重来，以便流程完整闭环。
24. 作为玩家，我能用方向键左右移动、按下键冲刺，以便完整游戏的手感完整。

### 作为接手这个仓库的开发者

25. 作为开发者，我有一条命令就能在本地装好 Unity、Hub、IDE 并激活许可，以便开始工作。
26. 作为开发者，我能在不开编辑器的情况下把五个工程的标签、构建场景、输入设置准备好，以便批量开工。
27. 作为开发者，我能用一个脚本把 Unity 的场景与预制体解析成可读结构，以便在不打开编辑器的情况下理解场景接线。
28. 作为开发者，我能把官方效果录像抽成时间轴拼图，以便对照确认行为节奏。
29. 作为开发者，我能让 Unity 在无界面模式下导入工程、编译脚本并跑一次测量，以便快速拿到模型实际尺寸。
30. 作为开发者，我能用一次构建命令产出 Windows 64 位玩家构建，以便交付。
31. 作为开发者，我能在编辑器里跑 Play 模式探针、驱动真实输入并断言可观察结果，以便证明达成条件真的成立。
32. 作为开发者，我能把每项工作中途提交到 issue 对应的 feature 分支，以便历史干净可审。
33. 作为开发者，我能在合并前用 PR 模板逐项勾选验收清单，以便不漏项。
34. 作为开发者，我每次跑 Unity 都带工程路径参数，以便不会在仓库根目录意外生成工程文件。

## Implementation Decisions

### 交付物结构

- 一共五个 Unity 工程，在仓库里平行编号：四个挑战各一个，完整游戏一个
- 选五个独立工程而不是一个大工程：四个挑战来自同一门课但素材与脚本互不通用，且考核要求四个挑战**分别**打包；独立工程让每个交付物的构建互不干扰
- 选平行目录而不是"主工程在根、其余在子目录"：两个考核任务是平级的，结构不对称会让人误判主次
- 每个工程带一份中文验收清单，放在统一的规格目录下，按交付物命名

### 编辑器与技术栈

- 编辑器固定在 Unity 2022.3 LTS 的最后一个补丁版
  - Unity 6 全系安装包在中国区 CDN 全部返回 404，直链与 Unity Hub 两条路都取不到
  - 2022.3 是课程官方支持的版本之一（6.0 / 6.3 / 2022.3 / 2021.3）
- 四个挑战统一采用课程的 2021.3 版起始文件
  - 6.0 版用新 Input System，但开包里不含 `.inputactions` 资源与生成的输入类，单独导入无法编译
  - 2021.3 版与其余两个挑战同代，本来就是旧版输入
- 保持教程技术原貌：legacy Input Manager、UGUI、内置渲染管线、Windows Mono 后端
  - 输入方式沿用 Unity 2022.3 的默认（旧版 Input Manager），项目设置里显式写死为该值
  - 不装 IL2CPP 模块：它依赖 Visual Studio 的 C++ 桌面开发工作负载，多一个失败点
- 每个工程补齐自己用到的自定义标签；Unity 内置标签（MainCamera、Player）不重复添加
  - 起始文件在标签缺失时不会报错，而是在运行时抛 `CompareTag` 异常，很难在导入阶段发现
- 每个工程设置：产品名、公司名、legacy 输入方式、构建场景列表

### 缺陷修复策略

- 缺陷分三类分开处理，不混在一次改动里：
  - **脚本逻辑**：按官方提示逐条改，保留原有类名与文件名（场景里靠 GUID 引用脚本）
  - **场景引用**：起始文件把预制体接错了位置，修正指向正确的预制体
  - **预制体参数**：碰撞体尺寸与模型实际尺寸脱节
- 狗的碰撞体按**实测**的模型包围盒重设，而不是凭观感调
  - 测量方式：在编辑器里实例化狗预制体，取所有渲染器的合并包围盒
  - 实测模型世界尺寸约 3.39 × 4.87 × 6.00，中心在脚底上方约 2.44
  - 原碰撞体世界尺寸约 2.32 × 38.76 × 78.09，长了约 13 倍、高了约 8 倍，这就是"球一靠近就被销毁"的真凶
- 球的销毁判定与狗的销毁判定分开，因为两者出界的轴不同：狗横向出界、球纵向出界
  - 用标签区分两类对象，避免球的生成位置靠近边界时被当成狗销毁
- 销毁球的分支同时输出"Game Over"提示，满足达成条件里"球落地要给出提示"的要求
- 加分项按官方列出的全部实现，不做取舍
  - 随机生成间隔用"自己排下一次"的方式实现，因为 Unity 的重复调用接口间隔是固定的
  - 连按刷狗用冷却时间限制
  - 摄像机加速附加粒子效果挂在焦点对象下

### 完整游戏

- 以作者公开发布的工程为基线，而不是从零重写
  - 该工程已包含全部精灵切片、动画、音频、预制体、两个场景与六个脚本
- 唯一缺失的功能是冲刺移动，需要自己实现：冲刺时长、冷却、额外速度、冲刺标志位，按帧时间推进
- 补上课程里的"冷热游戏"控制台练习与 C# 基础练习

### 仓库与流程

- 领域词汇单独维护一份词汇表，明确区分"考核任务""挑战""达成条件""加分项""起始文件""挑战项目""完整游戏""交付包""玩家构建"等容易混淆的说法
- 不可轻易回退的决策写 ADR：编辑器版本选择、五个独立工程的选择、保持教程技术原貌
- 每个交付物对应一个 issue，分支命名带 issue 号，提交信息用 Conventional Commits
- 不重写已推送的历史：评分要求真实开发历史，改写会显得像事后编造
- 提供贡献指南与 PR 模板，把验收清单、构建验证方式、Unity 的调用规范写进去

### 工具

- 场景与预制体解析脚本：把 Unity 的 YAML 解析成"对象名 / 位置 / 标签 / 挂了哪些脚本 / 脚本的序列化字段"，避免为了看一眼接线就开编辑器
- 工程初始化脚本：批量写入标签、构建场景、产品名、输入方式
- 录像抽帧与拼图脚本：把官方效果录像抽成时间轴拼图，一图看完整段行为
- 编辑器测量脚本：实例化预制体并输出模型包围盒与碰撞体实际尺寸

## Testing Decisions

### 什么是好测试

只断言**外部可观察行为**——玩家看得见、听得见、玩得到的结果，不断言脚本内部的实现细节。不测"这个变量被赋成了什么"，而测"球在接触狗的瞬间消失""球落地时控制台出现 Game Over""背景在没有结束时也在滚动"。

### 三层缝

**缝一：静态接线检查**（最低层，最快）
- 断言每个工程的自定义标签齐全、构建场景指向正确的场景、输入方式为旧版、场景里的预制体引用指向正确的资源
- 抓的是"工程能打开但一运行就报错"这一类问题，秒级完成
- 沿用现有的工程初始化脚本的写法

**缝二：Play 模式行为探针**（最高层，最接近玩家体验）
- 在编辑器里打开该交付物的场景，进入 Play 模式，驱动真实输入（按空格、点击、方向键），观察世界里的对象状态变化，断言达成条件与加分项是否成立
- 逐条对应验收清单：例如挑战二要断言"空格放出狗""狗沿左方向移动""球与狗接触时球被销毁""球落到下边界时输出 Game Over""狗出界被销毁""生成间隔在 3~5 秒之间""连按有冷却"
- 挑战三要断言"背景在游戏未结束时也在滚动""玩家刚体已赋值不抛空引用""两种障碍都会生成""背景重复时宽度取的是宽度不是高度""烟花出现在气球位置"
- 挑战四要断言"撞敌人时敌人被推向远离玩家的方向""道具五秒后消失""清空敌人后下一波敌人多一个""敌人朝玩家球门移动"
- 挑战五要断言"点击才销毁、移入不销毁""分数显示为 Score 加数值""难度改变生成速率""游戏结束出现重启按钮""倒计时归零结束游戏"
- 完整游戏要断言"主菜单进入游戏""玩家移动与冲刺""障碍生成间隔递减""扣血与失败画面""音乐跨场景不中断"
- 每个交付物一个探针脚本，跑完输出通过/失败清单

**缝三：构建产物冒烟**（交付层）
- 每个工程导出 Windows 64 位玩家构建
- 运行导出的程序，确认能启动、场景能加载、输入有响应
- 抓的是"编辑器里好好的、导出来就坏"这一类问题（平台相关、资源丢失、脚本裁剪）

### 验证顺序

先跑缝一（便宜），再跑缝二（验证行为），最后跑缝三（验证交付物）。任何一层失败就停下来修，不往下堆。

### 已有先例

仓库内已有工程初始化脚本与场景解析脚本可作为脚本风格与断言写法的先例；课程官方提供的效果录像是行为断言的对照基准。

## Out of Scope

- 不做 Unity 6 迁移，也不追新版本
- 不改用新 Input System、UI Toolkit 或 URP
- 不安装 IL2CPP 模块
- 不发布到 itch.io：课程用它演示发布流程，阶段一交 Windows 构建即可
- 不逐帧还原官方录像，不追求画面完全一致
- 不额外发明课程之外的玩法
- 不维护 Gitee 镜像（是否需要待与群里确认）
- 不重写已推送的 Git 历史
- 不追求完全无人值守：许可激活与最终交付包命名需要人工确认

## Further Notes

- **素材来源**：四个挑战的起始文件与素材从课程官方渠道直接下载，无需网盘；完整游戏的工程、精灵、动画、音频由作者公开发布，可直接取得。百度网盘与飞书私信这两条路都不必走
- **许可**：Unity Personal 免费许可需要在 Unity Hub 里登录 Unity 账号并申请，这一步必须人工完成，其余环节可自动化
- **Quiz 3**：挑战三那一集附带十题测验，答案要写进交付文档
- **提交包命名**：考核 PDF 未给命名规范，物联网方向的规范是"年级+专业+姓名+方向第一阶段"，最终以群里确认为准
- **提交时间**：群里尚未看到明确截止日期
- **Unity 调用规范**：不带工程路径参数启动编辑器时，Unity 会把当前工作目录当成工程，在仓库根目录生成工程文件——本仓库已踩过一次，已写进贡献指南
